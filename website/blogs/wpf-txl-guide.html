How TXL builds native Windows apps with WPF.

TXL is a compact language for desktop interfaces. Its compiler turns supported TXL project files into a WPF app for Windows—not a website, and not unrestricted access to every WPF feature.

How TXL works22 November 2026

Windows Presentation Foundation (WPF) is Microsoft's Windows desktop UI framework in .NET. Microsoft describes WPF as a Windows-only framework with controls, layout, data binding, graphics, media, text, and other desktop capabilities. TXL uses WPF for its generated runtime, while exposing a smaller, language-specific set of controls and behavior.

“Native Windows app” means an actual Windows desktop target

A TXL build opens as a regular Windows application window. It is not a browser page packaged in an app shell. The project controls a subset of window options such as title, icon, size, and mode. Its generated WPF interface can be run and visually checked on Windows.

That target is also a boundary: WPF does not run on macOS or Linux. TXL can validate source or cross-publish from elsewhere under supported SDK conditions, but that does not let you launch or visually test the WPF interface there.

What a small TXL interface looks like

TXL keeps a line-oriented source format with blocks delimited by parentheses. Here is the shape of a simple native window:

window (
  title: Hello TXL
  size: 720x480
  mode: normal
)

style (
  main:
    font = Segoe UI
    background = #111827
    color = #F3F4F6
)

group = home (
  layout = vertical
  text.headline = Hello, Windows
  button = Show a message
  action = alert("Built with TXL.")
)

Check the current grammar for exact supported property and action syntax. Layout groups support vertical, horizontal, and absolute positioning. Class-based click, hover, and key-down events exist; runtime state and simple dialogs are also documented.

TXL does not provide all features commonly associated with a full WPF project. For example, its current scope does not include hot reload, responsive constraints, theme switching, a component inspector, or a custom modal form builder. The implemented feature list states those boundaries explicitly.

From source to the Windows build

Install the .NET 9 SDK and the per-user txl command, then run txl --check in a project folder. The check validates TXL source and project metadata. On Windows, txl --preview launches a native preview; txl --build writes a distributable Windows x64 app beneath dist.

The standard build is self-contained, so TXL and a separately installed .NET runtime are not required on the target PC. “Self-contained” does not mean “one file”: media or other local project assets are copied to the app's content folder, so share the full output directory.

Microsoft's WPF overview and .NET publishing guide explain the platform and deployment model. For TXL-specific setup, follow the installation guide.

When might TXL be a useful fit?

TXL is designed for small desktop interfaces where its supported controls, layouts, actions, and state model are enough. The language guide and AllFeatures example let you inspect the actual syntax before deciding.

For applications that need arbitrary WPF APIs or framework features outside the TXL grammar, ordinary .NET/WPF development may be a better fit. A successful txl --check is a syntax check, not a substitute for testing keyboard focus, window rendering, app icons, media codecs, and app behavior on the Windows versions you intend to support.
